{% comment %} SPEC §11.4's filter builder, as a row of add-a-rule controls. Every word of vocabulary in here — which sources exist, which operators each value type takes, which operators take no value at all, what to call them, which sources this deployment cannot evaluate yet — comes from `filter_config`, which the view builds from `CONDITION_SCHEMA["x-brightbean"]` and the condition engine's own source registry. There is no second table of operators in this template, and that is the point: an operator added to apps/contacts/conditions.py shows up here with no edit. The rules live in Alpine state and are serialised into one hidden input on every change, so the form GETs a single `filter=` parameter that the server hands straight to the condition engine. Posting the rules as separate form fields would mean re-assembling the document server-side — a second parser for a language that already has one. Plain No filter — showing everyone.
