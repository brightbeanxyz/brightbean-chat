# BrightBean Chat API v1

A bearer-authenticated JSON API, plus signed outbound webhooks. Together they
support the scenario SPEC §21 phase 3 is accepted on: an inbound webhook from
somewhere else updates a contact through this API, starts a flow through this
API, and the result comes back as a signed outbound delivery — with no glue
code on either side.

The interactive reference is served by the deployment itself at
`/api/v1/docs`, and the machine-readable document at `/api/v1/openapi.json`.
This file is the narrative version, with a worked example per resource.

Base URL below is written as `https://chat.example.com`; substitute your own.

---

## Authentication

Issue a key from **Settings → Organization → API keys**. Keys are organization
level because they span every workspace in the organization (SPEC §4.1), but
each key acts inside exactly **one** workspace. Issuing one needs two things:
you are an organization owner or admin, *and* you hold `manage_api_keys` in the
workspace you are issuing into.

Send it as a bearer token:

```bash
curl https://chat.example.com/api/v1/contacts \
  -H "Authorization: Bearer bb_..."
```

Four things worth knowing before you build against it:

* **The key is shown once.** Only a keyed digest is stored, so nothing can
  recover it — if you lose it, revoke it and issue another.
* **Revocation is immediate.** There is no cache in front of it; the next
  request fails.
* **HTTPS only.** Outside development a bearer that arrives over plain HTTP is
  refused, because by then it has been logged by every hop that saw it.
* **There is no anonymous surface.** Every endpoint requires a key. `401` means
  the key is missing, malformed, unknown or revoked — deliberately the same
  answer for all four, so probing tells you nothing.

### Scopes

| Scope | Grants |
|---|---|
| `read` | List and read contacts, tags, custom fields and flows. |
| `write` | Everything `read` does, plus creating and updating contacts, tagging, setting field values, starting flows and sending messages. |

No scope grants key, channel, member or workspace-settings management. An API
key cannot mint another API key.

An endpoint your key's scopes do not cover answers `403`. That is different from
`404`, which is what you get for an object that does not exist **or** belongs to
another workspace — see [Errors](#errors).

## Rate limits

**10 requests per second, per key.** Over the limit you get `429` with a
`Retry-After` header. The window is one second wide, so the header is the exact
wait rather than a number to pad. Keys never contend with each other, so one
noisy integration cannot starve another in the same workspace.

(SPEC §17 describes this as a sliding window; the implementation is the
project's shared fixed-window limiter, `apps/common/ratelimit.py`. At 10 req/s
the difference is that a caller can occasionally get up to 19 requests across a
window boundary. One shared limiter with one set of failure modes was judged
better than a second implementation that agrees with it most of the time.)

## Requests

JSON in, JSON out. Bodies are capped at 256 KB and 20 levels of nesting.

**Unknown keys are rejected, not ignored.** A typo in a field name is a `422`
rather than a silently dropped value, and there is no way to smuggle a field
nobody validated into a create.

## Pagination

Every list endpoint answers with the same envelope:

```json
{
  "data": [ ... ],
  "has_more": true,
  "next_cursor": "eyJvIjo1MH0"
}
```

Pass `?limit=` (1–200, default 50) and `?cursor=`. **The cursor is opaque** —
echo back `next_cursor` and never construct one. Keep paging while `has_more` is
true.

There is deliberately no `total`. Counting a workspace's contacts costs more
than the page itself, and nothing in this contract promises it.

## Errors

Every non-2xx answer is the same document:

```json
{
  "error": {
    "code": "compliance_denied",
    "message": "This contact opted out of messages on this channel.",
    "detail": {"reason": "opted_out", "message_id": "0192f0c1-..."}
  }
}
```

Branch on `code`; it is stable. `message` is for a human reading a log and may
be reworded. `detail` carries structured extras where there are any.

| Code | Status | Meaning |
|---|---|---|
| `unauthenticated` | 401 | Missing, malformed, unknown or revoked key. |
| `forbidden` | 403 | The key is valid; its scopes do not cover this endpoint. |
| `not_found` | 404 | No such object in this key's workspace. |
| `payload_too_large` | 413 | Body over the size cap. |
| `invalid_request` | 422 | A field is missing, unknown or the wrong shape. See `detail.fields`. |
| `invalid_cursor` | 422 | The cursor was not one this API produced. |
| `invalid_field_value` | 422 | The value does not fit the custom field's type. |
| `body_too_deep` | 422 | The JSON body nests deeper than the limit. |
| `compliance_denied` | 422 | The compliance engine refused the send. `detail.reason` says why. |
| `no_api_trigger` | 422 | The flow has no enabled `api` trigger to fire. |
| `flow_not_runnable` | 422 | The flow has no published version, or no single entry node. |
| `rate_limited` | 429 | Over the per-key limit. |
| `server_error` | 500 | Something went wrong here. Nothing is echoed back. |

**An object belonging to another workspace answers `404`, exactly as a
non-existent one does.** That is deliberate: a `403` would confirm the id names
something real, and over a UUID space that confirmation is the only thing an
attacker was missing.

## Contacts

### List

```bash
curl "https://chat.example.com/api/v1/contacts?q=ada&limit=2" \
  -H "Authorization: Bearer bb_..."
```

```json
{
  "data": [
    {
      "id": "0192e8ab-1c3d-7f00-8000-2b1a0f9c4d21",
      "first_name": "Ada",
      "last_name": "Lovelace",
      "email": "ada@example.com",
      "phone": "+15550001",
      "locale": "en",
      "timezone": "Europe/London",
      "status": "active",
      "tags": [{"id": "0192e8ac-...", "name": "signed-up"}],
      "last_interaction_at": "2026-08-22T18:04:11.201Z",
      "created_at": "2026-08-20T09:11:00.004Z",
      "updated_at": "2026-08-22T18:04:11.201Z"
    }
  ],
  "has_more": false,
  "next_cursor": null
}
```

Filters, all optional and combinable:

| Parameter | Effect |
|---|---|
| `q` | Case-insensitive match on first name, last name, email or phone. |
| `tag_id` | Only contacts carrying that tag. |
| `status` | `active` (default) or `deleted`. |
| `created_after`, `created_before` | ISO 8601. A naive timestamp is read as UTC. Percent-encode the offset — a bare `+00:00` decodes to a space and is rejected; `Z` needs no encoding. |
| `updated_after` | ISO 8601. Useful for incremental syncs. |

### Create

```bash
curl -X POST https://chat.example.com/api/v1/contacts \
  -H "Authorization: Bearer bb_..." \
  -H "Content-Type: application/json" \
  -d '{"first_name": "Ada", "email": "ada@example.com"}'
```

`201` with the contact. Fields: `first_name`, `last_name`, `email`, `phone`,
`locale`, `timezone` — all optional, all defaulting to `""`.

A contact created here is recorded with `source="api"` for the consent audit
(SPEC §11.8). You cannot set that yourself.

### Read and update

```bash
curl -X PATCH https://chat.example.com/api/v1/contacts/0192e8ab-... \
  -H "Authorization: Bearer bb_..." \
  -H "Content-Type: application/json" \
  -d '{"phone": "+15550001"}'
```

A partial update: omitted fields are left alone. Send `""` to clear a field —
`null` is not a way to clear one, because the underlying columns are not
nullable.

### Tags

```bash
# Attach, creating the tag if this workspace does not have it yet
curl -X POST https://chat.example.com/api/v1/contacts/0192e8ab-.../tags \
  -H "Authorization: Bearer bb_..." \
  -H "Content-Type: application/json" \
  -d '{"name": "signed-up"}'
```

```json
{"id": "0192e8ac-4f21-7a10-8000-91b73c02ee55", "name": "signed-up"}
```

`201` when the tag was newly attached, `200` when it was already there — so a
retrying integration can tell a change from an idempotent no-op. Pass
`{"tag_id": "..."}` instead of `{"name": ...}` to attach an existing tag by id;
exactly one of the two.

```bash
# Detach, by id
curl -X DELETE https://chat.example.com/api/v1/contacts/0192e8ab-.../tags/0192e8ac-... \
  -H "Authorization: Bearer bb_..."
```

`204` whether or not it was attached — the end state is the same either way.
Removal is by id rather than by name because a tag name can contain anything,
including a slash.

### Custom field values

```bash
curl -X PUT https://chat.example.com/api/v1/contacts/0192e8ab-.../fields/0192e8ad-... \
  -H "Authorization: Bearer bb_..." \
  -H "Content-Type: application/json" \
  -d '{"value": 42}'
```

```json
{"field_id": "0192e8ad-...", "name": "Score", "type": "number", "value": 42}
```

The field's own type decides what a value may be; a mismatch is
`invalid_field_value`. Send `{"value": null}` to clear it. `GET
/api/v1/contacts/<id>/fields` lists every value set on a contact.

### Start a flow

```bash
curl -X POST https://chat.example.com/api/v1/contacts/0192e8ab-.../flows/0192e8ae-.../start \
  -H "Authorization: Bearer bb_..." \
  -H "Content-Type: application/json" \
  -d '{"trigger_key": "signup", "variables": {"plan": "pro"}}'
```

```json
{
  "execution_id": "0192e8af-...",
  "flow_id": "0192e8ae-...",
  "contact_id": "0192e8ab-...",
  "status": "running"
}
```

`202`. This fires the flow's **`api` trigger** (SPEC §10), which means it
respects everything a trigger does: the contact's advisory lock, the
supersede rule (one live execution per contact — a new start expires the old
one), and compliance on anything the flow then sends.

* `trigger_key` picks between several `api` triggers on the same flow. Omit it
  and the lowest-priority enabled one wins.
* `variables` is merged into the execution's variables and is available to
  `{{placeholder}}` rendering. Capped at 8 KB and 6 levels.
* `status` is `"queued"` and `execution_id` is `null` when another event held
  the contact's lock; the start was enqueued and will run in a moment. Still a
  `202`.
* A flow with no `api` trigger is `no_api_trigger`; an unpublished one is
  `flow_not_runnable`.

## Messages

```bash
curl -X POST https://chat.example.com/api/v1/messages \
  -H "Authorization: Bearer bb_..." \
  -H "Content-Type: application/json" \
  -d '{
        "contact_id": "0192e8ab-...",
        "connection_id": "0192e8b0-...",
        "body": {"text": "Your order has shipped."},
        "idempotency_key": "order-4711-shipped"
      }'
```

```json
{
  "id": "0192e8b1-...",
  "conversation_id": "0192e8b2-...",
  "contact_id": "0192e8ab-...",
  "status": "sent",
  "source": "api",
  "error": "",
  "created_at": "2026-08-23T09:14:02.481Z"
}
```

`201`. Text only in v1 — media, cards and buttons are authored in the flow
builder.

**`idempotency_key` is your retry story.** Send the same key twice and the
second call returns the first message instead of sending again. Omit it and one
is generated, which means the call is *not* idempotent; a network timeout you
retry could then send twice.

### Compliance refusals

A send the compliance engine refuses is `422` with `code: "compliance_denied"`
and a machine-readable `detail.reason`:

```json
{
  "error": {
    "code": "compliance_denied",
    "message": "This contact opted out of messages on this channel.",
    "detail": {"reason": "opted_out", "message_id": "0192e8b1-..."}
  }
}
```

| `reason` | What it means |
|---|---|
| `opted_out` | The contact opted out on this channel. Never retry. |
| `no_identity` | This contact has no address on this channel. |
| `no_opt_in` | Never given permission to be messaged on this channel. |
| `contact_deleted` | The contact has been deleted. |
| `outside_window` | The messaging window has closed and this platform offers no way to reopen it. |
| `needs_template` | Outside the window this platform requires an approved template. |
| `needs_tag` | Outside the window this platform requires an approved message tag. |
| `no_connection` | The address was captured before a channel connection existed. |

A refusal still records a failed message row, named by `detail.message_id`, so
the decision is auditable.

## Read-only lists

`GET /api/v1/flows`, `GET /api/v1/tags` and `GET /api/v1/fields` — the
vocabulary you need before you can do anything else. All paginated like
contacts. Flows accept `?status=draft|active|archived`; only an `active` flow
has a published version and can be started.

## Outbound webhooks

Configure endpoints per workspace under **Settings → Workspace → Webhooks**.
Each subscribed event becomes a POST to your URL.

### The payload

```json
{
  "id": "0192f0c1-8b1e-7c44-9f2a-3d5e6a7b8c9d",
  "event": "contact.tag_added",
  "workspace_id": "0192e8aa-...",
  "occurred_at": "2026-08-23T09:14:02.481Z",
  "data": {"contact_id": "0192e8ab-...", "tag_id": "0192e8ac-..."}
}
```

**Ids only, never content.** No message bodies, no names, no contact details.
Fetch what you need through the API with the ids you were given.

Headers:

| Header | Contents |
|---|---|
| `X-BrightBean-Signature` | `v1=` followed by the hex HMAC-SHA256. |
| `X-BrightBean-Timestamp` | Unix seconds, and part of what is signed. |
| `X-BrightBean-Event` | The event name, so you can route before parsing. |
| `X-BrightBean-Delivery` | Stable across retries. **This is your deduplication key.** |

### Events

| Event | `data` | Fires when |
|---|---|---|
| `contact.created` | `contact_id`, `source` | A contact is created, however it was created. |
| `contact.tag_added` | `contact_id`, `tag_id` | A tag is newly attached. Re-adding an existing tag fires nothing. |
| `message.received` | `contact_id`, `conversation_id`, `message_id`, `connection_id`, `platform` | An inbound message is persisted. |
| `execution.completed` | `contact_id`, `execution_id`, `flow_id`, `flow_version_id`, `preview` | A flow execution finishes successfully. |
| `broadcast.finished` | — | A broadcast completes. Subscribable now, delivered once broadcasts ship. |

### Verifying a delivery

The signature covers the timestamp, a literal `.`, and the **raw request
body** — on the bytes you received, before any JSON parsing or re-encoding.

```python
import hashlib, hmac, time


def verify(secret, headers, raw_body, tolerance=300):
    timestamp = headers["X-BrightBean-Timestamp"]
    presented = headers["X-BrightBean-Signature"]
    if abs(time.time() - int(timestamp)) > tolerance:
        return False
    signed = timestamp.encode() + b"." + raw_body
    expected = "v1=" + hmac.new(secret.encode(), signed, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, presented)
```

```javascript
const crypto = require("crypto");

function verify(secret, headers, rawBody, tolerance = 300) {
  const timestamp = headers["x-brightbean-timestamp"];
  const presented = headers["x-brightbean-signature"];
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > tolerance) return false;
  const signed = Buffer.concat([Buffer.from(`${timestamp}.`), rawBody]);
  const expected = "v1=" + crypto.createHmac("sha256", secret).update(signed).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(presented));
}
```

Three things that are not optional:

1. **Compare in constant time.** `==` on a signature is a timing oracle.
2. **Check the timestamp.** That is what makes a captured delivery
   non-replayable; 5 minutes is a sensible tolerance.
3. **Deduplicate on `X-BrightBean-Delivery`.** Delivery is at-least-once.

The `v1=` prefix exists so a future signing scheme can ship alongside this one.
Split on `=` and reject a version you do not implement.

### Delivery, retries and auto-disable

Answer `2xx` to acknowledge. Anything else — including a timeout or an
unreachable host — is a failure, retried on the standard backoff
(30s, 2m, 10m, 1h, 6h). All attempts of one delivery share a
`X-BrightBean-Delivery` id and send byte-identical bodies.

After **100 consecutive failed deliveries** the endpoint is switched off and the
workspace admins are notified. A failure here means one delivery that exhausted
all its retries, not one HTTP attempt — a receiver that blips for a minute never
gets close. Any success resets the counter. Re-enabling the endpoint in the
settings page clears it too.

### The SSRF guard

Every delivery goes through the project's outbound guard
(SECURITY-BASELINE §6). It resolves your hostname once and pins the connection
to the checked address, re-validates every redirect, and **refuses loopback,
link-local (cloud metadata), multicast, reserved and private addresses**.

So a webhook pointed at `http://127.0.0.1:9000/hooks` is accepted by the form —
it is a syntactically valid URL — and refused at delivery, showing up as a
`blocked` row in the endpoint's delivery log. A self-hosted deployment whose
receiver genuinely lives on its own network sets
`EXTERNAL_REQUEST_ALLOW_PRIVATE=true`, which relaxes the private-range rule
alone: loopback and the metadata service stay denied whatever it is set to.

Blocked deliveries are not retried — the refusal would be identical — but they
do count towards the auto-disable limit.

### The delivery log

The endpoint's settings page shows the last 50 deliveries: event, outcome,
response code, duration and attempt number. Request and response **bodies are
never stored** — a receiver's error page can echo back the URL it was called
with, and a URL can carry a token.

## The phase-3 scenario, end to end

The whole point, in six calls. An external form posts to your automation
platform; the platform does the rest with nothing but this API.

```bash
KEY="bb_..."
BASE="https://chat.example.com/api/v1"
FLOW="0192e8ae-..."   # from GET $BASE/flows

# 1. Create or find the contact
CONTACT=$(curl -s -X POST "$BASE/contacts" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"first_name": "Ada", "email": "ada@example.com"}' | jq -r .id)

# 2. Enrich them
curl -s -X PATCH "$BASE/contacts/$CONTACT" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"phone": "+15550001"}' > /dev/null

# 3. Tag them
curl -s -X POST "$BASE/contacts/$CONTACT/tags" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"name": "signed-up"}' > /dev/null

# 4. Start the welcome flow
curl -s -X POST "$BASE/contacts/$CONTACT/flows/$FLOW/start" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"trigger_key": "signup", "variables": {"plan": "pro"}}'
```

With an endpoint subscribed to `contact.created`, `contact.tag_added` and
`execution.completed`, your receiver gets three signed deliveries — the last one
when the flow finishes. No polling, and no code in BrightBean Chat.
